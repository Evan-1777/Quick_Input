## 1. 背景与目标

当前版本（v0.2.0）的预设文本列表按 `updated_at DESC, id DESC` 排序，编辑任意条目都会把它推到列表顶部，无法固定顺序；快捷面板只能通过点击侧栏分组切换，缺少纯键盘方式；面板的「全部」会展示所有未分组文本，与「用分组筛选常用内容」的使用方式冲突。

本次交付解决三点：

1. 管理列表支持拖动调整预设文本顺序，顺序持久化并被快捷面板复用；编辑条目不再改变位置。
2. 快捷面板中按 `[` / `]` 在「全部 + 各分组」之间循环切换，保留当前关键字与标签筛选。
3. 快捷面板默认隐藏未分组文本，并在设置页提供一个可持久化的开关；管理窗口仍然展示未分组。

不在本次范围内：

- 分组与标签本身的拖动排序，二者继续按名称排序。
- 快捷面板内的拖动排序，面板仍以检索与键入为主。
- 发布版本号调整、跨设备同步、排序动画。

排序对象假设：需求只写了「手动拖动排序」，本次按预设文本列表实现；若需要分组排序，侧栏拖放与面板循环顺序需一并扩展。

## 2. 现状与探索结论

- 排序写死在 store 查询中，`Snippet` 模型没有顺序字段；新建与编辑都会刷新 `updated_at`，因此编辑会改变位置。
- MyGo 的列表控件已提供拖动重排能力（`ListState.Reorder`），与多选（`ListState.Selection`）兼容，与 `DragSelect` 互斥。本项目管理列表只用多选，可直接复用，无需自绘拖放。
- 拖放回调给出被拖行的索引与「放到哪一行之前」的目标索引；多选时被选行按升序整体移动。
- 快捷面板的搜索框是单行文本输入。MyGo 的 `OnTextKey` 只接收不产生文本的按键（方向键、Esc、Enter 等）；`[` / `]` 会先作为文本写入绑定值。已验证的可行路径是：在面板每帧构建的开头读取绑定值、剥离方括号并按净方向切换分组（多枚方括号钳制为一步），再取数据构建列表。探针确认同一帧内即可完成剥离与重新取数，不会出现一帧空列表。
- 面板与管理窗口共享同一份内存快照和过滤函数，面板差异应封装在面板侧，避免改变管理窗口的过滤语义。
- 面板的分组行是普通容器、标签是 Toggle；点击任一筛选后焦点离开搜索框，后续按键不再进入输入框。已用 headless 探针复现，现有上下键同样受影响；需要在筛选变更后主动把焦点交还搜索框。
- 应用已有 settings 键值表与设置页卡片结构，可承载一个布尔开关，不需要新增依赖或数据表。

## 4. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 顺序存储 | snippets 增加整数 `position`，每次落位后全量重编号为 0..n-1 | 无间隙、无小数漂移，查询与回填都简单；个人库规模下 O(n) 写入可接受 | 间隔编号或小数中点：避免全量写，但要处理精度耗尽与归一化，复杂度不划算 |
| 新条目位置 | 置顶（`MIN(position) - 1`） | 保持升级前「新建后在顶部」的直觉；编辑不触碰 position | 追加到末尾：会改变现有使用习惯 |
| 排序作用域 | 只排预设文本；分组与标签继续按名称排序 | 需求未要求分组排序，分组顺序还会牵动面板循环；避免未证实抽象 | 给分组也加 position：schema、侧栏拖放、循环顺序全部扩大一层 |
| 过滤视图拖动 | 以目标索引及其后第一条未移动的可见行为锚点，插入其前；无锚点则末尾 | 与列表控件的回调语义一一对应；隐藏行保持相对顺序，行为可解释 | 禁止过滤时拖动：多一条状态判断，且用户无法在小范围里调整 |
| 方括号处理 | 面板构建开头从绑定关键字中剥离 `[` / `]`，按净方向步进分组；单帧内多枚方括号钳制为一步 | MyGo 的可打印按键不会进入 `OnTextKey`；值路径在 Windows（按键+文本）与 Linux（仅文本）一致，无需自绘输入控件 | 拦截键盘事件：可打印文本由文本客户端直接写入编辑器，应用层拿不到；自绘可编辑文本代价过大 |
| 方括号取舍 | `[` 向前、`]` 向后；关键字中出现的方括号（含粘贴文本）一律视为指令并从查询中移除，一次最多翻一步 | 行为确定、实现最短，符合「快速翻动」的定位；钳制步数避免越界并消除粘贴多括号的跳变 | 仅在关键字为空时生效：与需求不符，翻组时还得先清空搜索；按净数量翻多步：多枚方括号会越界，且不符合一按一翻 |
| 面板隐藏未分组 | 面板取数后再剔除未分组，不改共享过滤函数与管理窗口 | 最小差分；管理窗口的「未分组」筛选语义原样保留 | 给共享 FilterState 加字段：两端的重置与测试都要跟着改，扩大扰动 |
| 未分组开关 | settings 键值持久化，默认关闭；设置页用开关行；开启后「未分组」重新出现在面板筛选与循环中 | 贴合需求中的「默认」语义，也保留找回未分组内容的入口 | 固定隐藏：无法找回，且面板首次使用时新建的未分组内容会直接消失 |
| 设置页开关 | 沿用现有卡片与行样式，`ui.Switch` + 可访问名称；错误统一由页面级错误行展示，保存失败保留原状态 | 与快捷键设置一致的交互与错误模型；错误不落在相邻的快捷键卡片内，避免误读 | 每张卡片各放一条错误：两个设置源会重复展示同一条信息 |
| 面板空态 | 有筛选时保持「没有匹配的预设文本」；无筛选且未分组被隐藏、没有任何可见条目时显示「暂无分组预设文本」并提供「打开管理窗口」 | 避免「新建后消失」的误导，文案陈述事实 | 保持「暂无预设文本」：与实际数据不符 |
| 面板按键路径 | 仍由搜索框承载，不新增根级方括号快捷键；筛选变更后（分组、标签、空态清除筛选）主动把焦点交还搜索框 | 维持「面板键盘只有一条路径」的既有约束；点击分组会清空焦点、点击标签会移走焦点，回焦后上下键与方括号都恢复可用 | 只加 `KeepFocus`：只保持当前焦点；焦点已在 Toggle 上时（Tab 导航后）点击分组仍不会回到搜索框 |
| 依赖 | 不新增依赖，不改键入、窗口、托盘链路 | 改动只涉及 store 与 app | 无 |

## 5. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 旧库迁移中断导致顺序全为 0 | 🔴 高 | `ALTER TABLE` 与回填放在同一事务；用旧 schema 文件库测试迁移后的显示顺序 |
| 单连接下 PRAGMA rows 未关闭就开启事务，迁移等待锁 | 🟡 中 | 读完 `PRAGMA table_info` 的 rows 并关闭后再开事务；旧库迁移测试覆盖整条路径 |
| 方括号在输入法组合或全角模式下不触发 | 🟡 中 | 记录为已知限制；英文输入与直接输入方括号的行为由测试覆盖 |
| 单帧内多枚方括号使步数超出分组数，`steps[-1]` 崩溃 | 🔴 高 | `cycleGroup` 把步数钳制为 -1/0/+1，一次按键最多翻一步；补「步数绝对值超过分组数」与 `tt.Type("[[[[")` 用例 |
| 点击分组、标签或空态「清除筛选」后焦点离开搜索框，方括号与现有上下键失效 | 🔴 高 | 筛选变更后调用搜索框 `Focus()`；补「点击分组后再输入方括号」用例，标签与清除筛选路径同样回焦 |
| 过滤视图下拖动落点与隐藏行交叠，用户预期不一致 | 🟡 中 | 锚点规则固定为「目标可见行之前」，测试覆盖过滤场景；不做隐式跨组调整 |
| 拖动手势与双击编辑、行内按钮冲突 | 🟡 中 | 复用控件内置拖动阈值与「拖动不算点击」语义；视图测试覆盖拖动后未打开侧边页 |
| 方括号无法作为搜索字符；粘贴含方括号的文本会被消费（净方向非 0 时触发翻组） | 🟡 中 | 记录为已知限制；步数钳制避免多枚方括号崩溃；不额外拦截粘贴，需求只定义按键行为 |
| 全量重编号在大库下的写放大 | 🟢 低 | 个人库规模可接受；代码注释标注 O(n) 上限与升级为间隔编号的路径 |
| 设置开关写库失败后界面与实际不一致 | 🟢 低 | 先写库再更新内存值；失败时开关回到原状态，并在设置页页面级错误行展示 |
| 列表顺序改为手动后，既有测试中的行序与选中次数失效 | 🟡 中 | 明确旧顺序回填规则；逐条修正面板测试的初始行与方向键次数 |
| 面板隐藏未分组后，首次使用新建的未分组内容不可见 | 🟡 中 | 空态明确提示并引导打开管理窗口；设置开关可恢复展示 |

## 7. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：顺序持久化 | 强（schema、查询、写入与现有测试共用同一契约） | 无（后续全部依赖） | 主线 | 数据层要先定型，拆出去只会增加契约漂移 |
| Phase 2：拖动排序 | 强（依赖 Phase 1 接口与列表多选语义） | 低（改动小且与 Phase 3 共享状态文件） | 主线 | 单文件级改动，冷启动与重新读盘成本高于任务本身 |
| Phase 3：面板快捷键与未分组 | 强（依赖现有面板、过滤与设置页结构） | 低（两处视图共用 App 字段） | 主线 | 需要连续推演方括号路径与空态，主线处理更直接 |
| Phase 4：验证与文档 | 强（依赖实际测试结果与代码差异） | 无（串行收口） | 主线 | 需要按失败结果即时修复 |

> **协同结论**：本次改动集中在 store 与 app 两包、文件高度重叠且严格串行，委托无法形成实质并行，全部由主线执行，不派发 Subagent。
